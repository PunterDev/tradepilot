# Disaster Recovery Runbook

RTO and RPO are MANAGEMENT DECISION REQUIRED until formally approved. Do not claim automatic failover unless tested and evidenced.

| Scenario | Impact | Detection | Immediate Response | Fail-Safe Behavior | Recovery Steps | Escalation | Evidence To Retain |
| --- | --- | --- | --- | --- | --- | --- | --- |
| Supabase unavailable | App data reads/writes, auth state, billing ledger, and analytics unavailable or degraded | Health checks, DB errors, support reports | Pause risky write operations if needed; monitor vendor status | Do not fabricate billing or credit state | Follow Supabase recovery guidance; restore only from verified backup if needed; verify Flyway/schema/data | SEV-1/SEV-2 depending duration/data risk | Vendor status, logs, DB errors, restore evidence |
| Render unavailable | Backend API unavailable | Health check failure, Vercel/API errors | Roll back deployment if caused by release; review Render status | Frontend should fail visibly; no false success | Restore previous deployment or wait for provider recovery; verify health and logs | SEV-1/SEV-2 | Render logs, deploy IDs, health checks |
| Vercel unavailable | Frontend unavailable | Uptime monitor, customer reports | Check Vercel status and last deploy | Backend remains source of truth | Roll back frontend deploy or wait for provider recovery | SEV-2 | Vercel logs, deploy IDs |
| Stripe unavailable | Checkout, portal, subscription reconciliation impacted | Stripe API/webhook errors | Pause billing promises if widespread | Do not grant credits/entitlements without verified source of truth | Wait for Stripe recovery; replay/verify webhooks; reconcile DB | SEV-2/SEV-1 for billing integrity | Stripe status/events, processed events, reconciliation |
| OpenAI unavailable | AI features degraded | AI failure metrics, logs | Use existing safe fallback behavior where implemented | Cached/no-data paths should not consume credits incorrectly | Retry after vendor recovery; monitor AI costs/failures | SEV-3/SEV-2 | AI metric records, vendor status |
| Qdrant unavailable | Trading Memory degraded | startup validation, health service, vector errors | Disable/degrade memory-dependent features if necessary | Core trade data remains in PostgreSQL | Validate collection after recovery; retry indexing | SEV-3/SEV-2 | Qdrant validation, retry records |
| Databento unavailable | Trade Replay market data unavailable | provider errors, replay failures | Return provider unavailable errors; avoid excessive retries/cost | Do not show fabricated market data | Retry after recovery; verify cost controls | SEV-3 | Provider errors, request IDs |
| Resend unavailable | Verification/password reset/contact emails delayed | email metrics/logs | Communicate support impact; avoid logging links | Accounts may be blocked from verification/reset until recovery | Retry/resend after provider recovery | SEV-2/SEV-3 | Email metrics, provider status |
| GitHub unavailable | Source/CI/deploy pipeline limited | provider status, failed workflows | Avoid emergency untracked code changes | Existing production should remain running | Resume normal change workflow after recovery | SEV-3 | GitHub status, workflow logs |
| Domain/DNS provider unavailable | App routing/domain changes unavailable | DNS errors, monitoring | Avoid untested DNS changes; use provider support | Existing DNS may continue if cached | Restore known-good DNS settings | SEV-1/SEV-2 | DNS records, provider ticket |
